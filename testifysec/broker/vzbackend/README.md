# Native VZ backend preparation and local execution

This internal Go package prepares approved files and offers a single-use `Prepared.Run` for the local Aflock VZ session service. It does not install a customer component, enable the production Darwin broker peer path, or change Linux/Docker behavior. The service administrator supplies `Assignment`; workspace content, CLI settings and model output do not choose it. The normative [agent policy contract](../../../../../docs/architecture/pushgate-agent-policy-contract.md) keeps profile approval separate from enrollment, signing identity and push authority.

`New(Assignment)` validates a value copy. Each `Prepare(ctx, rawDSSE)` executes the exact pinned native admission program afresh. The native program authenticates the original signed profile under its embedded trust. This package requires its strict v2 output, exact envelope and payload hashes, tenant/deployment/profile assignment, current validity, and the signed `darwin-vz/v1` backend manifest pin. Legacy v1 output cannot authorize preparation. No network, human-session fallback, environment-selected trust, or runtime package download is used.

The exact `backend.json` schema is `testifysec.aflock.vz-backend/v1`. Its fixed target and protocol fields are `darwin-arm64`, `linux-arm64`, `testifysec.vm-job/v3`, `testifysec.vm-result/v3`, and `HCMDL2`. The manifest hash covers original JSON bytes, with duplicate keys, unknown/missing fields, null coercions, changed number tokens and invalid Unicode refused. Its four `{sha256,size}` roles map to fixed filenames:

| Role | File | Maximum bytes | Prepared mode |
| --- | --- | ---: | --- |
| host | `hc-vm` | 64 MiB | 0500 |
| kernel | `kernel` | 128 MiB | 0400 |
| rootDisk | `root.ext4` | 2 GiB | 0400 |
| provenance | `build.json` | 256 KiB | 0400 |

`backend.json` is bounded to 16 KiB and retained read-only. Installation and complete stages contain exactly those five files. Provenance is opaque data; it cannot supply paths, executables or authority. A bounded 32-byte Mach-O header check classifies the approved host as ARM64 executable format. It does not validate all load commands, code signatures, entitlements, absence of fixture compile flags, or runtime availability.

The package walks held directory descriptors, checks root/service ownership and non-writability by other users (allowing root-owned sticky ancestors), and refuses symlinks, nonregular files and multiple hard links. Reads compare file identity, owner, mode, size, modification/change times before and after use. Streamed copies hash exact bytes into a fresh service-owned 0700 stage using exclusive creation. Staging is disjoint from installation and the admission executable. Same-service-UID code and root remain trusted; this is not protection against their arbitrary concurrent replacement. Darwin and Linux file preparation are supported; other hosts refuse through the custody layer. No platform is declared execution-qualified here.

`Prepared.Inspect(ctx)` rechecks custody, exact inventory and copied hashes. The admitted validity window is checked after copying and during each inspection. `Close` cancels inspection, invalidates the handle and deletes only known files inside its positively owned stage; it is idempotent. Unknown content or uncertain child cleanup retains state and returns `cleanup_failed`. There is no stale-stage reuse, automatic crash recovery or fsync/durability guarantee. Context cancellation is checked between bounded I/O operations; an indefinitely stalled filesystem syscall is not claimed interruptible. The execution method re-admits immediately before start and retains ownership through observed stop/drain.

The pinned admission program has a five-second deadline and bounded stdout. Its own process group must be observed absent after completion; surviving descendants cause refusal, and uncertain cleanup preserves the stage. The trusted verifier must not deliberately escape its process group. The diagnostic accepts regular-file, pipe or socket stdin. For inherited pipes it creates a pollable CLOEXEC duplicate, closes that owned input on timeout, SIGINT or SIGTERM, joins the cancellation callback, then restores the original descriptor flags. It exclusively reads its stdin. Abrupt process/kernel failure can leave a retained stage.

The developer diagnostic accepts only `vz-backend-check --assignment /protected/assignment.json`, with bounded raw DSSE on stdin. It prepares, independently inspects, closes, and emits sanitized hashes plus `scope: backend-preparation-only` and `executionEnabled: false`; no stage path or reusable execution grant is returned. Failure output contains a fixed code. A future service caller must load assignments from protected service configuration, never present this diagnostic as production admission for arbitrary user configuration.

Run `go test ./vzbackend ./cmd/vz-backend-check` and the same packages with `-race` from the broker module. Unit fixtures exercise strict parsing, assignment/custody/size/hash refusals, expiry/cancellation, fresh stages, read-only copies, tamper detection, bounded cleanup and real native-child/input lifetimes. Their direct validity seam is test-only. The separate [backend UAT](../../vm/BACKEND.md) packages retained real V3 files, invokes compiled Rookery DSSE admission, and checks exact copies and cleanup without booting a VM. The preparation-only report remains separate from session execution UAT; no Docker execution result, hardware attestation or per-tool evidence is created here.

`Prepared.Run(ctx, RunRequest)` accepts bounded prompt, timeout and regular-file material values from the protected service, plus its private gateway config path/digest and session ID. It consumes the handle before re-admission, rejects subsequent Run/Inspect calls, and supports only Darwin ARM64. It constructs exact job/v3 bytes and config/v4 internally with the already approved host, kernel, root, backend manifest pin, one CPU, 1024 MiB and fixed transport ports. No backend stage paths are exposed. The per-session gateway config must bind the same session, profile and backend; its existing socket is explicitly mode 0666 beneath a held service-owned 0700 parent. The service separately owns gateway process and socket identity checks. The generated job, gateway config and host config are retained read-only and rehashed with their exact three-file inventory after fresh native admission and again after observed shutdown. `ConfigSHA256` binds the generated host config separately from the gateway config digest.

`NotAfter` is a final launch-freshness bound supplied after the service's fresh platform identity check. It is checked after admission and file verification; it does not claim continuous authorization or a live human identity. The request timeout is 1–45 seconds, the host configuration allows another 10 seconds, and the process supervisor begins cancellation no later than request timeout plus 35 seconds. Cancellation signals the owned host group, allows up to 35 seconds for graceful VM shutdown, then kills and waits at most another 5 seconds. Forced termination is always cleanup-unsafe. The owned stdout/stderr pipes distinguish actual EOF from read failure or forced reader closure, cap retained output, and require bounded drain and observed group absence. Trusted native helpers must not escape their groups. These are service lifecycle checks, not a substitute for untrusted-code isolation.

`RunResult` retains original bounded observation/v4 bytes and their SHA256, exact job bytes and hash, input bindings, and observed host exit/pipe/group facts. Nested guest result/v3 is validated without converting it into Linux/Docker evidence. Completion requires matching job/nonce/frame/material/capture hashes, worker exit zero, complete output and capture, and actual VM stopped plus serial/job/relay drains and serial EOF. Worker failure can have safe cleanup; malformed or contradictory observations cannot. Captured files and worker-reported tool output do not establish independent per-tool process attestations. The original host still reports `admissionIntegrated:false`; native admission and online identity are distinct outer service facts.

Run never deletes the backend stage. `Close` cancels and joins an active Run before considering removal; the service must stop its gateway first. `Retain` closes descriptors and invalidates the handle while preserving known state with `cleanup_failed`, for uncertain gateway or scratch cleanup. Unknown process/VM termination, missing EOF, or changed runtime input custody latches retention even if a later Close is attempted. Post-run byte/custody checks use their own bounded context, so cancellation or profile expiry cannot skip them. There is no stale-run retry, automatic crash recovery, publication, fsync durability guarantee or release/hardware qualification.
